Repair work protocol:
Start from the actual failed check and current files. Distinguish declaration/binding defects, Rust implementation defects, test connection defects and external execution problems. A behavioral counterexample can originate in any of the first three. Inspect original equations and the composed call before assigning blame.
Give a short diagnosis tied to available evidence; request material if a necessary definition or caller is missing. Return the concrete change with the diagnosis in the same response when possible. Domain knowledge comes from semantic-adaptation, rust-generation or the connection guide; this protocol does not prescribe one representation.
After a repeated failure compare the executed change and diagnostic with the previous attempt. Revise the hypothesis or expand evidence, rather than restating a fix. Do not add clone, stronger bounds, numeric casts or fallback branches merely to silence a diagnostic. Do not modify source requirements, tests, expected answers or the input domain to make a candidate pass.
Compilation validates types, loading validates effective declarations, and behavioral checks validate observed cases. Keep these claims separate. A reference conflict is not permission to choose whichever reference the candidate matches. Explicit range errors are not successful tests.
During review identify substantive findings by code location, source condition, alternative and reason to change or retain. Include support implementations and adapted-away source operations. A clean review may accept unchanged code. Static cost judgments are not measured speedups. No performance results are supplied to guide repairs.
