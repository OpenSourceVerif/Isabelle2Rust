# 近邻工作与方法定位：初步核对

> 历史讨论，非当前协议：本文的 B 路线定位和候选研究机制未作为当前方案采纳。当前优先直接从 Isabelle 生成 Rust，不要求为了区别已有工作而增加机制；见 [paper-01-v0.1](../plans/paper-01-v0.1.md)。以下保留当时的阅读与推测记录。

检查日期：2026-10-23。当前范围只考虑 B：在已有 Stage-2 Rust 上优化。不启动 C，不启动付费模型实验。

这是针对近邻工作的定向阅读，不是完整系统综述，也不能证明某个候选方向无人做过。下面区分论文已有机制、我们的判断、尚待验证的假设。

## 当前判断

原先的“LLM 改写—编译—测试—性能反馈—保留候选”应定位为实验基础设施和通用基线，不能单独作为新方法贡献。AFP 数据来源和 Isabelle 语言场景也不自动产生方法新颖性。流程复杂度、agent 数量不是贡献指标。

## 必须重新考虑的前提

1. 不应先画复杂框架，再寻找能够填入的“创新”。先识别通用优化方法在本项目上实际失败的机制。
2. “B 只能修改单个函数且不能调整任何辅助函数”的限制是此前讨论中的设计提议，不是已经由实验证实合理的研究边界。任何放宽都需要显式更新协议；本次不修改它。
3. List-Index.last_index 的现有 Stage-2 实现包含 reverse、index 和长度计算。单遍扫描是明显方向，但属于主要算法结构变化，不能悄悄作为严格 B 的成功案例。该任务目前更适合接通流程，而非自动充当论文主例。
4. 只给模型更多源码与定理，不等于形式保证，也不一定优于匹配预算的通用上下文。

## 候选研究问题：翻译信息能否改善剩余开销的诊断与优化

待验证假设：把 Rust 中的开销映射回 Isabelle 定义与翻译步骤，区分源算法本身的成本、翻译产生的表示成本，以及 Stage-2 分析保守留下的成本，可以改善 B 的目标选择和语义约束，而不只是增加提示词长度。

候选机制（尚未实现、未证明新颖）：

- 对齐 Isabelle 常量、Stage-1 与 Stage-2 位置，定位剩余克隆、闭包、分配等现象。
- 根据代码检查和 profiling 解释剩余开销；必要时为优化器补充未应用变换的原因记录，不把猜测写成诊断事实。
- 构造有来源的优化任务：修改区域、相关调用、可执行源定义、适用条件、明确的输出关系及可检验行为。
- 在这些约束下运行通用模型改写循环，记录接受和拒绝原因。

这里真正待检验的是信息如何改变目标选择、允许的修改和检查方式。PerfR 已有规则、前提与上下文，因此不能把该候选机制简单称为“首次语义感知优化”。

## 判断是否值得继续的方法

先在几个真实剩余开销上比较：

- 通用 Rust 优化，提供相同工具与预算。
- 通用优化加原始 Isabelle 源码上下文。
- 通用优化加经过来源对齐、前提整理和诊断的结构化信息。

保持输入域、允许修改范围、模型、总预算和最终测试可比。模块消融需要区分来源对齐、诊断、语义约束的作用，而不是一次加入所有东西。如果只是更多 token 导致改善，要设置相应控制。正式比较应有不参与规则/提示词开发的条目。

先找到并分析失败案例，再决定最终架构。没有观察到稳定差异时，不应为了包装论文而继续堆叠模块。仍可考虑严谨的实证研究，但其价值须来自新的、可复核的发现。
